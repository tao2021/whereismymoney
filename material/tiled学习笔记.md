# Tiled SGEMM 学习笔记

> 学习路径：naive_sgemm 为什么慢 → 共享内存分块（tiling）如何优化
> 参考文件：`src/kernels/naive_sgemm.cuh`、`src/kernels/tiled_sgemm.cuh`
> 矩阵规模：M = N = K = 1024（float，行主序）

---

## 一、naive SGEMM 为什么慢

### 1.1 代码回顾

```cuda
int row = blockIdx.y * blockDim.y + threadIdx.y;
int col = blockIdx.x * blockDim.x + threadIdx.x;
if (row < M && col < N) {
    float sum = 0.0f;
    for (int k = 0; k < K; ++k) {
        sum += A[row * K + k] * B[k * N + col];
    }
    C[row * N + col] = sum;
}
```

每个线程计算 `C[row][col]` 的一个元素，需要读 A 的一行（K 个）+ B 的一列（K 个）。

### 1.2 慢的根本原因：重复读取 + 低算术强度

以 M=N=K=1024 量化：

| 项目 | 数值 |
|---|---|
| 每个线程读取 | 2K = 2048 个元素 |
| 总线程数 | M×N ≈ 105 万 |
| **实际总读取** | ≈ **21.5 亿次** |
| A、B 数据总量 | ≈ 210 万个 |

**同一个元素平均被读 1024 次！**

- `A[row][k]` 被计算 C 第 row 行的 N=1024 个线程重复读
- `B[k][col]` 被计算 C 第 col 列的 M=1024 个线程重复读
- 每次都是从全局内存读，零复用

### 1.3 为什么读多了就慢（memory-bound）

- 总读取字节 ≈ 8.6 GB，若带宽 900 GB/s，传输需 ~9.5 ms
- 总 FLOPs = 2MNK ≈ 21.5 亿，按峰值 10905 GFLOPS 只需 ~0.2 ms
- **计算单元大部分时间在等数据** → 内存带宽受限

## 二、核心概念：合并访问与广播

### 2.1 warp 的划分规则（代码里没有显式 warp）

warp 是硬件调度单位，划分规则：

```
linear_tid = threadIdx.x + threadIdx.y * blockDim.x + ...
每连续 32 个 linear_tid 组成一个 warp
```

`threadIdx.x` 变化最快。当 `blockDim.x = 32` 时，一个 warp = 固定 `threadIdx.y` + `threadIdx.x = 0..31`。

### 2.2 判断口诀

**看地址公式里含不含 warp 内变化的索引（col）：**

| 表达式 | warp 内情况 | 结论 |
|---|---|---|
| `A[row*K+k]`（不含 col） | 32 线程访问同一地址 | **广播**（1 次事务） |
| `B[k*N+col]`（含 col 且连续） | 32 个连续地址 | **合并**（1 次事务） |

两者都高效，都是 1 次内存事务。**naive 慢不在"合并与否"，在"访问次数太多 + 零复用"。**

### 2.3 算术强度

$$\text{算术强度} = \frac{\text{FLOPs}}{\text{内存字节数}}$$

- naive：$2MNK\ \text{FLOP} / (2MNK \times 4\ \text{byte}) = 0.25\ \text{FLOP/byte}$
- ⚠️ 代码注释写的 "1 FLOP/byte" 有误，漏了 float = 4 字节的换算
- 现代 GPU 平衡点约几十 FLOP/byte，naive 差上百倍

## 三、Tiled SGEMM：共享内存分块

### 3.1 tile 的含义

**tile = 从大矩阵切出来的 32×32 小方块**。共享内存装不下整个 1024×1024 矩阵，所以切成小块，一次搬一块、算一段。

### 3.2 坐标变量总表

| 变量 | 含义 | 在 A 中 | 在 B 中 |
|---|---|---|---|
| `by = blockIdx.y` | 行块索引 | A 的行块 | — |
| `bx = blockIdx.x` | 列块索引 | — | B 的列块 |
| `t`（循环变量） | K 维块索引 | A 的列块 | B 的行块 |
| `ty = threadIdx.y` | 块内行偏移 | A 块内行 | B 块内行 |
| `tx = threadIdx.x` | 块内列偏移 | A 块内列 | B 块内列 |

- A 的 tile = `(by, t)`：第 by 行块 × 第 t 列块
- B 的 tile = `(t, bx)`：第 t 行块 × 第 bx 列块
- **`t` 是 A、B 沿 K 维的公共对齐轴**（矩阵乘法要求 A 第 t 列块 × B 第 t 行块配对）

### 3.3 矩阵切分

- A（M×K）：行按 `by` 切 32 段，列按 `t` 切 32 段
- B（K×N）：行按 `t` 切 32 段，列按 `bx` 切 32 段
- 1024 能被 32 整除 → 完美均分，无边界残留

加载规则（一一镜像，不改变排列）：

```cuda
As[ty][tx] = A[by*32+ty][t*32+tx]
Bs[ty][tx] = B[t*32+ty][bx*32+tx]
```

### 3.4 三段式循环

```cuda
float sum = 0.0f;                     // 跨 t 循环累加，不重置
for (int t = 0; t < numTiles; ++t) {
    // ① 加载：分工把 A、B 的 tile 搬进共享内存
    As[ty][tx] = A[row*K + (t*32+tx)];
    Bs[ty][tx] = B[(t*32+ty)*N + col];

    __syncthreads();                  // ② 等所有线程加载完

    for (int k = 0; k < 32; ++k)      // ③ 计算 32 项，累加
        sum += As[ty][k] * Bs[k][tx];

    __syncthreads();                  // ④ 防覆盖，再同步
}
```

### 3.5 分批累加：小窗口扫过大点积

点积是加法，可分段累加：

$$C[row][col] = \underbrace{\sum_{k=0}^{31}}_{t=0} + \underbrace{\sum_{k=32}^{63}}_{t=1} + \cdots + \underbrace{\sum_{k=992}^{1023}}_{t=31}$$

- 共享内存是**滚动窗口**：每次只装当前 t 段的 32 个 A 值 + 32 个 B 值
- `sum` 跨 t 循环持续累加，32 次后累满 1024 项
- **不需要一次取齐横向/纵向 1024 个数据**，靠时间上的分批解决

### 3.6 分工加载 + 共享使用（核心）

- 每个线程只**搬 2 个**元素（1 A + 1 B），但计算时**用 64 个**（As 一行 + Bs 一列）
- 差的 62 个是**其他线程搬的**——这是"共享"二字的本质
- `As` 每行被 32 个线程（同 ty）共享；`Bs` 每列被 32 个线程（同 tx）共享

**对比：如果每个线程只搬自己需要的 64 个 → 总搬运 65536 个（32 倍），且退化成 naive。**
整块方案通过分工，每个元素只搬 1 次，总搬运 2048 个。

## 四、为什么快：量化对比

### 4.1 读取次数

| | naive | tiled |
|---|---|---|
| 全局读取（每线程） | 2K | 2K/32 |
| 全局总读取 | $2MNK$ | $2MNK/32$ |
| 共享读取 | 0 | ≈ 2K |

总读取次数大致不变，但**贵的全局读 ÷32，换成便宜的共享读**。

### 4.2 算术强度提升

$$\text{tiled 算术强度} = \frac{2MNK}{(2MNK/32)\times 4} = \frac{32}{4} = 8\ \text{FLOP/byte}$$

比 naive 的 0.25 提升 32 倍。

### 4.3 性能数据

| Kernel | 耗时 | GFLOPS | 占 cuBLAS |
|---|---|---|---|
| Naive | 3.308 ms | 649 | 9.9% |
| Tiled (32×32) | 2.598 ms | 827 | 12.6% |
| Tensor Core (WMMA) | 1.264 ms | 1699 | 25.9% |
| cuBLAS | 0.328 ms | 6556 | 100% |

峰值 FP32 = 10905.6 GFLOPS。

### 4.4 为什么只提升 27%（非理论 32 倍）

新瓶颈：
1. **共享内存带宽**：计算阶段大量共享访问
2. **`__syncthreads()` 同步开销**：每个 tile 2 次同步
3. **跨 block 重复读取**（见下）
4. **占用率**：1024 线程/block + 8KB 共享内存限制驻留 block 数

## 五、block 间的关系

1. **无时间先后**：1024 个 block 并行、无序调度，不能假设顺序
2. **无数据冲突**：A、B 只读；C 各写自己的 32×32 块，互不重叠
3. **共享内存 block 私有**：不可跨 block 访问，block 间只靠写回 C 汇总

### 跨 block 重复读取（tiled 的残留重复）

三层对比：

| 版本 | 每个元素被读次数 |
|---|---|
| naive | 1024 次 |
| tiled | **32 次**（block 内复用已消除，跨 block 的 32 次还在） |
| 理论极限 | 1 次 |

`A[row][k]` 被 32 个 block（同 by、不同 bx）各读一次 → tiled 把重复从 1024 降到 32，正是提速 32 倍的来源。

---

## 六、易错点与口诀

1. **"共享 32 次" ≠ 分 32 块**：是一个元素被 32 个线程复用，数据 1 份、位置 1 个
2. **"取位置变了" ≠ 没优化**：全局读 ÷32 + 共享读补上，总次数不变但总成本 ÷32
3. **"加载整块" 不浪费**：分工加载（每线程搬 1 格）+ 共享使用（读一行/列），比"各自搬自己需要的"省 32 倍
4. **合并 vs 广播**：看地址公式含不含 warp 内变化的索引
5. **算术强度**：naive = 0.25（注释的 1 有误），tiled = 8

## 七、后续优化方向

| 方向 | 解决的问题 |
|---|---|
| Bank Conflict Free | 共享内存 bank 冲突 |
