# 共享内存的 Bank 机制学习笔记

> 日期：2026-11-12
> 关联文件：`src/kernels/bank_conflict_free_sgemm.cuh`、`tiled_sgemm.cuh`、`naive_sgemm.cuh`

---

## 1. Bank 是什么、谁分的

- **Bank 是硬件划分的**，不是软件分的。
- 共享内存物理上并不是一整块连续 RAM，而是被 GPU 硬件设计成 **32 个并行存储模块**，每个模块就是一个 bank。
- 每个 bank 宽度 = **4 字节**（正好一个 `float` / `int`）。
- bank 数量 32 是芯片架构固定的，编译器和程序员都改不了（个别架构可用 `cudaDeviceSetSharedMemConfig` 在 4/8 字节 bank 模式间切换，但数量固定）。

### 为什么硬件要分 bank

GPU 的调度单位是 **warp = 32 个线程**，理想情况下一个 warp 的 32 个线程应同时完成一次共享内存读写：

- 32 个线程访问 **32 个不同 bank** → 32 个模块同时工作 → **1 个时钟周期**完成。
- 多个线程访问**同一个 bank 的不同地址** → 该 bank 忙不过来 → 排队**串行** → **bank conflict**。

> 类比：32 车道的收费站，每条车道（bank）一次只放行一辆车（一个地址）。

---

## 2. 地址 → bank 的映射规则

硬件按"字地址"把连续内存轮流分到 bank 上：

```
bank = (byte地址 / 4) % 32
```

也就是连续的 float 依次落进 bank 0, 1, 2, …, 31, 0, 1, … 循环往复。

| 字地址（float 序号） | 0 | 1 | 2 | … | 31 | 32 | 33 |
|---|---|---|---|---|---|---|---|
| bank | 0 | 1 | 2 | … | 31 | 0 | 1 |

---

## 3. 为什么"列号一致 = 挤在同一个 bank"

关键在于 **行主序存储** + **行宽正好是 32**。

对 32×32 行主序数组 `arr[i][j]`，字偏移为：

```
offset = i * 32 + j
bank   = (i * 32 + j) % 32 = j
```

因为 `i × 32` 永远是 32 的倍数，模 32 恒等于 0，只剩下 `j % 32 = j`。

**结论：bank 编号只由列号 j 决定，与行号 i 无关。**

### 用具体数字验证（第 5 列，j = 5）

| 元素 | 字偏移 = i×32+5 | bank = offset % 32 |
|---|---|---|
| `arr[0][5]` | 5 | 5 |
| `arr[1][5]` | 37 | 37 % 32 = 5 |
| `arr[2][5]` | 69 | 69 % 32 = 5 |
| `arr[31][5]` | 997 | 997 % 32 = 5 |

整列 32 个元素全部落在 bank 5。

原因：每行正好 32 个 float = 恰好走完一整圈 bank（0→31），下一行又从 bank 0 重新开始，所以所有行的"同一列"都停在"同一圈的同一位"上。

---

## 4. Bank 冲突 vs 容量（两个不同维度）

容易混淆的点：**"挤在同一个 bank" 不是数据物理堆进同一个 4 字节格子**。

| 维度 | 问题 | 答案 |
|---|---|---|
| 容量问题 | 共享内存放不放得下数组？ | 看共享内存总大小 |
| bank 冲突 | 同一时刻 32 个线程是否挤同一个 bank 端口？ | 看访问地址的 bank 分布 |

### 容量方面

- 共享内存大小有限，每个 SM 通常 **48KB / 96KB / 164KB / 228KB**（依架构）。
- 整个共享内存被平均分成 32 个 bank，每个 bank 容量 = 总大小 / 32。
- 例如 96KB 共享内存，每个 bank 有 3KB = 768 个 float，**不存在"塞不下"的问题**。
- 本程序 tile 数组：`As[32][33]` + `Bs[32][33]` ≈ 8.2KB，远小于 48KB。

### 冲突方面

- bank 是**访问通道/端口**，不是存储槽位。
- 每个 bank 每个时钟周期只能服务一个地址。
- 32 个线程同时访问同一 bank 的不同地址 → 排队 32 次 → **32 路 conflict**。
- 数据各自有独立地址、互不拥挤，拥挤的只是"同一时刻的访问通道"。

> 类比：32 个柜台（bank），钱存在各自保险柜（不会放不下）。问题只在于 32 个人同时都要去 5 号柜台办业务，只能排队。

---

## 5. Bank 与 block/grid 的关系

**核心结论：bank 划分规则与 block/grid 无关。**

- block/grid 是**线程组织层次**：决定哪些线程在哪个 block、处理全局内存哪块数据。
- bank 是**共享内存内部的物理结构**：决定共享内存地址如何映射到物理 bank。
- 两套东西互不影响，无论 grid/block 怎么排，bank 规则都一样（固定 32 个、每个 4 字节）。

注意区分：

- **共享内存本身是 per-block 的**（每个 block 有独立一份）。
- **bank 划分规则对所有 block 通用**。

### 冲突到底与什么有关

只取决于 **一个 warp 里 32 个线程在同一时刻访问的地址分布**：

```
是否冲突 = f(warp 内 32 个线程的访问地址)
```

访问地址又由**索引写法**（`Bs[k][tx]` vs `Bs[tx][k]`）和**数组维度**（32 vs 33）决定。

所以冲突 = "索引方式 × 硬件固定 bank 规则"的结果，与 grid/block 排列、矩阵大小无关。

---

## 6. Bank Conflict Free 程序思路

核心手段只有一句：**给共享内存数组第二维加 1 个 padding 元素**。

```cpp
__shared__ float As[TILE_SIZE][TILE_SIZE + 1];  // 原来是 [TILE_SIZE][TILE_SIZE]
__shared__ float Bs[TILE_SIZE][TILE_SIZE + 1];
```

### padding 为什么有效

加 padding 后 `arr[32][33]`：

```
offset = i * 33 + j
bank   = (i * 33 + j) % 32 = (i + j) % 32   // 因为 33 % 32 = 1
```

每往下一行整行平移 1 个 bank，列访问就不再"回到原位"。第 5 列变成：

| i | bank = (i + 5) % 32 |
|---|---|
| 0 | 5 |
| 1 | 6 |
| 2 | 7 |
| … | … |
| 31 | 4 |

32 个线程正好铺满 32 个不同 bank → 零冲突。

---

## 7. naive / tiled / bank conflict free 对比

| 维度 | naive | tiled | bank conflict free |
|---|---|---|---|
| 共享内存 | 无 | 有（tile 分块） | 有（tile + padding） |
| 全局内存读取量 | 每线程读整行 A + 整列 B（2·M·N·K） | 减少 TILE 倍 | 同 tiled |
| 数据复用 | 无 | 每个元素复用 TILE_SIZE 次 | 同 tiled |
| B 的全局访问 | 列访问，不合并（主瓶颈） | tile 加载合并 | 同 tiled |
| 共享内存 bank conflict | 无（没有共享内存） | 看访问方式 | 通过 padding 消除 |
| 算术强度 | 极低，memory-bound | 高 | 同 tiled |

### 逐层递进

1. **naive**：直接对全局内存做点积。A 行访问没问题，但 B 是列访问不合并；且无数据复用，同一元素被反复从全局内存读。慢在**带宽**。
2. **tiled**：用共享内存分块缓存，`As[ty][k] * Bs[k][tx]` 只读共享内存，全局内存只加载一次、复用多次。解决**带宽**问题。
3. **bank conflict free**：进一步消除共享内存内部 bank conflict，让共享内存访问达到满吞吐。

---

## 8. 易错点：主 kernel 与转置 kernel 的区别

`bank_conflict_free_sgemm.cuh` 里有两个 kernel：

### 主 kernel（防御性 padding）

```cpp
sum += As[ty][k] * Bs[k][tx];
```

warp 内 `ty` 固定、`tx` 变化：

- `As[ty][k]`：所有线程同地址 → **广播**，无冲突。
- `Bs[k][tx]`：同一行连续地址 → **无冲突**。

此布局下本来就无冲突，`+1` 更多是防御性/教学性写法。

### 转置 kernel（真正体现 padding 威力）

```cpp
sum += As[ty][k] * BsT[tx][k];
```

此时 `BsT[tx][k]` 中 `tx` 变化 → **不同行、同一列 k**，是真正的列访问：

- 无 padding（`[32][32]`）：bank = `(tx*32 + k) % 32 = k` → 32 路冲突。
- 有 padding（`[32][33]`）：bank = `(tx + k) % 32` → 无冲突。

> 注意：文件头注释把 `Bs[k][tx]` 标成 "column access" 是不准确的，那是行访问；真正的列访问是 `Bs[tx][k]`（转置 kernel 中的情况）。

---

## 9. 一句话总结

naive → tiled → bank conflict free 是一条完整优化链：

1. **先减少全局带宽浪费**：分块复用（tiled）。
2. **再消除共享内存内部访问冲突**：+1 padding。

`+1 padding` 的精髓：把行宽从 32 改成 33，让每行错开 1 个 bank，列访问就从"全挤一个 bank"变成"均匀铺满 32 个 bank"。

## 10. 两个 kernel 的详细区别与效率对比

### 区别

| | `bank_conflict_free_sgemm_kernel` | `bank_conflict_free_transposed_sgemm_kernel` |
|---|---|---|
| B 的存储方式 | 正常存：`Bs[ty][tx]`（行主序原样） | 转置存：`BsT[tx][ty]`（加载时索引交换） |
| 计算访问 | `Bs[k][tx]`（同一行连续） | `BsT[tx][k]`（不同行同一列） |
| padding 的作用 | **多余**（本来就无冲突） | **必需**（去掉就有 32 路冲突） |

### 两者都有 bank 冲突吗？

当前代码里两个都加了 padding，所以**两个都是无冲突的**。但前提不同：

- **主 kernel**：不加 padding 也无冲突。`Bs[k][tx]` 是行访问（连续地址）→ 天然无冲突；`As[ty][k]` 是广播 → 无冲突。它的 `+1` 是"锦上添花"（多余）。
- **转置 kernel**：不加 padding 会有 32 路冲突。`BsT[tx][k]` 是真正的列访问：
  - 无 padding：bank = `(tx*32 + k) % 32 = k` → 32 路冲突。
  - 有 padding：bank = `(tx + k) % 32` → 无冲突。
  - 加载写入 `BsT[tx][ty]` 同理，不加 padding 也是 32 路写冲突。

### 运行效率区别

两者都加 padding 后，共享内存事务数完全一样：

| 访问 | 主 kernel | 转置 kernel |
|---|---|---|
| `As[ty][k]` | 广播（1 次事务） | 广播（1 次事务） |
| B 的读取 | `Bs[k][tx]` 连续 → 1 次事务 | `BsT[tx][k]` padding 后 → 1 次事务 |
| B 的加载写入 | `Bs[ty][tx]` 连续 → 1 次事务 | `BsT[tx][ty]` padding 后 → 1 次事务 |

**结论：两者效率几乎相同**，差异在噪声范围内。

> 真正的差异价值在于教学：它展示"同一份计算，换一种访问方式（转置后列访问）就会产生冲突，而 padding 能修复"。

## 11. 什么是行访问、什么是列访问

判断标准：**warp 里 32 个线程访问同一数组时，谁在变、谁固定**。

- **行访问**：32 个线程访问**同一行、不同列** → 内存地址**连续**。
- **列访问**：32 个线程访问**不同行、同一列** → 内存地址**跳跃**（步长 = 行宽）。

### 结合代码

- `Bs[k][tx]`：变化的 `tx` 是**列下标**，行下标 `k` 固定 → 扫同一行 → **行访问**。
- `BsT[tx][k]`：变化的 `tx` 是**行下标**，列下标 `k` 固定 → 扫同一列 → **列访问**。

### 为什么行访问无冲突、列访问有冲突

行主序数组，bank 公式：

```
行访问：bank = (i*32 + j) % 32 = j   → j 在变 → 32 个不同 bank ✅
列访问：bank = (i*32 + j) % 32 = j   → j 固定 → 全同一个 bank ❌
```

| | 谁在变 | 内存地址 | bank | 是否冲突 |
|---|---|---|---|---|
| **行访问** | 列下标（tx） | 连续 | 各不相同 | ✅ 无冲突 |
| **列访问** | 行下标（tx） | 步长 = 行宽 | 全相同 | ❌ 冲突 |

> 口诀：**warp 内变化的若是列下标 → 行访问（安全）；变化的若是行下标 → 列访问（需要 padding）**。

---

## 12. `As[ty][k]` 为什么无冲突（广播）

看某一次迭代（k 固定）时，一个 warp 里 32 个线程都在读 `As[ty][k]`：

1. **`ty` 在 warp 内不变**：`blockDim = (32, 32)`，线性编号 = `ty * 32 + tx`，一个 warp = `tx = 0..31`、`ty` 固定的那一组。
2. **`k` 在同一次迭代里对所有线程相同**：`k` 是循环变量，`#pragma unroll` 展开后每次迭代 `k` 是常量，所有线程同步执行同一次迭代。

于是 32 个线程读的是**同一个地址** → 硬件 **broadcast（广播）**：1 次事务把数据发给 32 个线程。

### 广播 ≠ 冲突

| 情况 | 是否冲突 |
|---|---|
| 32 个线程读**同一个地址**（广播） | ✅ 无冲突，1 次事务 |
| 32 个线程读**不同地址、但落在同一 bank** | ❌ 冲突 |

`As[ty][k]` 属于第一种——地址完全相同，连冲突的可能都没有。`k` 虽然跨迭代从 0 变到 31，但每次迭代都是一次独立访问，每次内部所有线程 k 相同，所以 32 次迭代是 32 次广播，没有一次冲突。

---

## 13. `ty` 在 warp 内不变：是硬件行为，不是程序"聪明"

**结论：不是程序聪明，是硬件聪明。** 分三层：

1. **`ty` 不变是数学必然**：CUDA 固定规则——一个 warp = 线性线程编号连续的 32 个线程。`线性ID = tx + ty * blockDim.x`，`blockDim.x = 32` 时，32 个连续 ID 正好是 `tx=0..31`、`ty` 固定的那一组。程序唯一"有意"的地方只是把 `blockDim.x` 设成 32。

2. **每个线程各自算地址，互不知晓**：每个线程的寄存器里有自己的 `tx`、`ty`、`k`，独立执行 `As[ty][k]`，没有通信、没有商量，只是"碰巧"算出相同地址。

3. **广播是硬件在访问瞬间处理的**：共享内存访问单元（LSU/交叉开关）同时拿到 warp 的 32 个请求地址，在访问瞬间比较：
   - 地址完全相同 → 广播 1 次；
   - 地址不同但不同 bank → 并行 1 次；
   - 地址不同但同 bank → 排队串行（conflict）。

> 类比：32 个人各自在纸条上写柜台编号同时递进窗口，窗口工作人员（硬件）一看全是"5 号"，只去 5 号取一次、复印 32 份。递纸条的人互相不知道对方写了什么。

## 14. 主 kernel：加 padding 与不加 padding 效果相同

对 `bank_conflict_free_sgemm_kernel` 而言，加不加 `+1` padding **效果完全一样**，因为它的所有共享内存访问本来就无冲突。

逐个访问点验证（不加 padding，`As/Bs[TILE][TILE]`，warp 内 `ty` 固定、`tx=0..31`）：

| 访问点 | 访问模式 | bank | 是否冲突 |
|---|---|---|---|
| 加载 `As[ty][tx]` | 同一行连续地址 | `tx` 各不相同 | ✅ 无冲突 |
| 加载 `Bs[ty][tx]` | 同一行连续地址 | `tx` 各不相同 | ✅ 无冲突 |
| 计算 `As[ty][k]` | 所有线程同一地址（广播） | 同地址 | ✅ 无冲突 |
| 计算 `Bs[k][tx]` | 同一行连续地址 | `tx` 各不相同 | ✅ 无冲突 |

所以：

```
有 padding → 0 冲突
无 padding → 0 冲突
性能：完全相同（padding 只是多占一点点共享内存）
```

**真正需要 padding 的是转置 kernel**（见第 8、10 节）。

## 15. 转置是如何实现的

核心只有一行——写入时交换下标：

```cpp
BsT[tx][ty] = B[bRow * N + col];   // 正常应写成 Bs[ty][tx]
```

- 正常 kernel：`Bs[ty][tx]` → 行对行、列对列，**原样存放**。
- 转置 kernel：`BsT[tx][ty]` → **行下标写 `tx`、列下标写 `ty`**，行和列对调。

取 `t=0, bx=0`（此时 `bRow=ty`、`col=tx`），即 `BsT[tx][ty] = B[ty][tx]`：

| 线程 (tx, ty) | 读全局元素 | 存入位置 |
|---|---|---|
| (0, 0) | B[0][0] | BsT[0][0] |
| (0, 1) | B[1][0] | BsT[0][1] |
| (1, 0) | B[0][1] | BsT[1][0] |
| (2, 3) | B[3][2] | BsT[2][3] |

规律：`B[行][列]` 被放到 `BsT[列][行]`，行、列对调 = 转置。

### 计算时如何读回来

线程 `(tx, ty)` 需要 `B[k][col]`（k 为收缩维度）。按存储规则 `B[k][col]` 存在 `BsT[col][k]`，而 `col` 对应线程的 `tx`，所以读 `BsT[tx][k]` 正好取回。

### 两个细节

1. **全局内存读取仍合并**：加载时 `col = bx*TILE_SIZE + tx` 随 tx 变化、`bRow` 固定，全局地址 `bRow*N + col` 连续 → coalesced，不受影响。
2. **共享内存写入是"散布"的，靠 padding 保平安**：写 `BsT[tx][ty]` 时 warp 内 `tx` 变化、`ty` 固定 → 每个线程写不同行同一列（列写）。无 padding：`tx*32 + ty` 全落 bank `ty` → 32 路写冲突；有 padding：`tx*33 + ty` → bank `(tx+ty)%32` → 无冲突。

---

## 16. 非 32×32 能否转置

**能，但前提是 tile 必须是正方形**（`blockDim.x == blockDim.y == TILE_SIZE`）。

转置只是"把 `[ty][tx]` 写成 `[tx][ty]`"的下标交换，与具体数字无关。只要 `tx`、`ty` 取值范围相同（正方形 tile），交换下标永远合法。

- 若是**长方形 tile**（如 16×32），`tx`、`ty` 范围不同，直接照抄会越界或错位，需把数组声明成 `[C][R]` 并相应改代码。

### 但防冲突效果与尺寸有关

转置写入 `BsT[tx][ty]`（tx 变化）是列访问，加 padding 后：

```
bank = tx * (TILE_SIZE + 1) + ty  (mod 32)
```

要 32 个 `tx` 落到不同 bank，需 `tx * (TILE_SIZE + 1) mod 32` 互不相同，即 `gcd(TILE_SIZE + 1, 32) = 1`（`TILE_SIZE+1` 为奇数）：

| TILE_SIZE | TILE_SIZE+1 | 与 32 是否互质 | +1 padding 效果 |
|---|---|---|---|
| 32 | 33（奇数） | ✅ | 无冲突 |
| 16 | 17（奇数） | ✅ | 无冲突 |
| 24 | 25（奇数） | ✅ | 无冲突 |
| 15 | 16 | ❌ gcd=16 | 仍 16 路冲突（padding 失效） |
| 31 | 32 | ❌ gcd=32 | 仍 32 路冲突（padding 失效） |

> 另外，前面"warp 内 `ty` 固定、`tx` 变化"的分析默认 **TILE_SIZE ≥ 32**；若 TILE_SIZE < 32，一个 warp 会横跨多行，冲突分析完全不同。

**总结**：转置的"写法"和尺寸无关（正方形即可）；防冲突的"效果"和尺寸有关（依赖 `TILE_SIZE+1` 是否为奇数、warp 是否恰好一行）。

## 17. 为什么 `tx` 在一个 warp 中会变化

关键：`tx = threadIdx.x` 是 CUDA 的**内置变量**，**每个线程有自己的、不同的值**，不是所有线程共用一个值。

- CUDA 启动 kernel 时同时跑成千上万个线程，每个线程执行**同一份代码**，但读到的 `threadIdx.x` 不同——像每个工人有自己的工号。
- 一个 warp = 32 个连续线程，`blockDim.x = 32` 时这 32 个线程的 `threadIdx.x` 正好是 0~31。

所以当 32 个线程同时执行 `BsT[tx][k]`：

| 线程 | 它的 tx | 读的地址 |
|---|---|---|
| 线程 0 | 0 | `BsT[0][k]` |
| 线程 1 | 1 | `BsT[1][k]` |
| … | … | … |
| 线程 31 | 31 | `BsT[31][k]` |

这就是 **SIMT（单指令多线程）**：同一行代码，所有线程一起执行，但数据（threadIdx）各不相同。

- "warp 内 `tx` 变化" = **32 个线程各拿着 0~31 的不同 tx**，不是同一个线程的 tx 随时间变。
- 对比 `ty`：同一 warp 内 `ty` 相同，是因为 warp 按"连续 32 个线性编号"分组，一组恰好是 `ty` 固定、`tx=0..31`。
